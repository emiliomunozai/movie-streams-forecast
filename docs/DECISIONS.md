# Decision log

The 15 decisions that shaped this solution, how each came about, and why.

I led the design and made every call; Claude Code (Claude Opus 5.5) drafted the implementation, which I reviewed and verified. **Origin** says who raised it: **Me** = my direction or a gap I flagged, **Proposed** = Claude laid out options and I chose, **Brief** = required by the challenge.

| # | Decision | Origin | How it came about | Why |
|---|---|---|---|---|
| 1 | **Architecture: one core, thin adapters, one Docker image, a flat repo** (`src/` = `checks`, `pipeline`, `monitoring` + `cli`, `app`; `infra/` Terraform; `tests/`; `data/` `models/` `output/`) | Me | I set the architecture up front: a live, deployable solution that can move platforms, the least code possible, and one code path for the batch job, the app and the tests. Later I had it audited to remove redundant functions and tests. | All logic is in pure functions (`checks`, `pipeline`, `monitoring`). The CLI, the UI and the tests call them, so the batch job and the app can't drift apart. Five Python files, no framework layers. Changing platform changes Terraform, not Python. |
| 2 | **Reproduce the notebook's preparation, reuse the model as-is** (Python 3.13, scikit-learn 1.8.0 pinned) | Brief | Before building, I walked through the notebook's training logic (May → June labels, the split, the baseline) until it was clear. | The brief says no retraining or refitting. A pickle only loads safely with the versions it was saved with. Proved by rebuilding the notebook's training table (2005 rows / 738 movies) and an independent re-check: 321/321 predictions match. |
| 3 | **Pluggable checks on the raw files: fail vs warn** | Me | I asked for a pre-pipeline module of checks we can keep adding to, then for casing/spelling checks and for every error to come with a short, ready-made fix prompt for an AI agent. | Fail when the output would be wrong (missing columns, negative counts, empty keys, duplicated movies, bad ids, spelling variants like `netflix`); warn when the model copes (missing attributes are imputed). Messages name CSV lines. |
| 4 | **Unmatched movies are predicted and warned about; unseen categories are reported** | Proposed | Raised while checking the brief's coverage; I chose to predict and report rather than drop. | The brief needs a prediction for every May combination, and the model's imputers handle missing metadata. The encoder silently zeroes unknown categories, so they go into `summary.json`. |
| 5 | **Month-agnostic: month from the file** | Me | I questioned why everything was tied to May and asked for a month-agnostic pipeline. | The monthly AWS job runs without code changes. Locally and in the app the month is read from the data (0 or several months fail loudly, `--month` overrides); on AWS it comes from the file name `YYYY-MM.csv`, so no Lambda. |
| 6 | **SageMaker Processing Job**, not Batch Transform or an endpoint | Me | I chose a Processing Job over Batch Transform and a real-time endpoint, to keep the batch script unchanged between local and AWS. | Runs our script as-is on files. Batch Transform expects already-prepared rows (we need a groupby and a join); endpoints are real-time, which isn't needed. `ml.t3.medium` is plenty for a few hundred rows. |
| 7 | **Either monthly file triggers the pipeline; the first run waits** (S3 → EventBridge → SageMaker Pipeline) | Me | I flagged that only the consumption file triggered and asked how EventBridge would know both files had arrived, then had it reworked. | Upload order doesn't matter: the run for the first file finds the other missing, logs "waiting" and exits 0; the second runs. A corrected re-upload re-runs its month. No Lambda, no schedule, no ordering convention for upstream. |
| 8 | **Our own image in ECR**, tagged by git SHA | Proposed | Follows from #1 (one image) and #2 (pinned versions). | Prebuilt SageMaker scikit-learn images stop at 1.4-2; the pickle needs 1.8.0. The same image runs locally, on Render and on SageMaker (identical predictions on arm64 and amd64). |
| 9 | **Model in versioned S3, chosen by the `ModelUri` parameter** | Proposed | Accepted as the simplest way to swap models later. | A new model needs no image rebuild, and every run records which model it used. v1 is uploaded by Terraform, so a fresh `apply` can run. |
| 10 | **One folder layout, locally and in S3** (`data/`, `models/`, `output/`), predictions partitioned by month | Me | I asked for the folders to look exactly the same locally and in S3. | The repo is a working example of the bucket, so a path means the same thing everywhere. `output/predictions/input_month=YYYY-MM-DD/` gives a predictable path for downstream and for Evaluate, idempotent reruns, and is Athena-friendly. |
| 11 | **Monthly movie metadata snapshots** (`s3://…/data/movies/YYYY-MM.csv`) | Me | I caught that a single reference catalog was wrong, since the metadata also changes monthly. | Titles and ratings change every month; one overwritten catalog would give reruns look-ahead data. The run waits for the month's snapshot instead of using a stale one. |
| 12 | **Track accuracy monthly, don't retrain** | Me | I asked for an MLOps view comparing accuracy month by month; we agreed retraining stays out of scope. | Scoring last month's predictions against this month's file stays within "use the existing model" and closes the MLOps loop. Retraining is documented as future work. The history holds only real measurements (seeded with the notebook's v1 holdout). |
| 13 | **No training data at inference, nor in the repo** | Proposed | Part of my lean-repo cleanup (README, `.dockerignore`, fewer tests). | The repo ships only the inference example. Drift is compared against saved stats (`models/v1/drift_reference.json`). The tests that prove the notebook is reproduced read the training files from the challenge package and skip without them. |
| 14 | **Streamlit UI on Render instead of an HTTP API** | Me | I wanted a live demo with a UI and a ModelOps dashboard, and challenged Streamlit vs Flask; Render replaced Hugging Face when Docker Spaces turned out to need PRO. | Downstream reads S3, so no API is needed. Streamlit gives upload, tables, charts and a ModelOps dashboard in plain Python. Render builds our Dockerfile unchanged. |
| 15 | **Least privilege, and a deliberately small scope** | Me | I reviewed the risks of a public repo and a live deployment and set the bar: least privilege, and only the infrastructure the brief needs. | A pipeline role that only starts jobs and passes the job role; a job role scoped to its S3 prefixes and ECR repo; an EventBridge role for one pipeline. Left out on purpose and documented: KMS, VPC, remote state, multiple environments; the container stays root until SageMaker's mounted folders are tested with a non-root user. |
